# 麦当劳支付 H5 MVP 验证说明

## 验证目标

本 MVP 只验证 `create-order` 返回的 `payH5Url` 能否安全、稳定地交接给浏览器和手机扫码环境，不负责创建订单，也不会自动支付。

需要确认四件事：

1. 二维码在另一台手机上扫码后能否打开；
2. 是否必须使用微信或支付宝内置浏览器；
3. 是否依赖创建订单设备上的 Cookie 或登录态；
4. 支付完成后页面如何回跳，以及 `query-order` 多久能查询到成功状态。

## 使用方式

1. 使用麦当劳 MCP 创建一笔已明确取得用户确认的低金额测试订单。
2. 复制响应中的原始 `payH5Url`，同时记录 `orderId`、实付金额和 `expirePayTime`。
3. 打开 EasyInput 的“通话”页面，在“支付链路 MVP”区域粘贴 `payH5Url`。
4. 点击“在浏览器显示二维码”。默认浏览器会打开一个仅绑定到 `127.0.0.1` 的临时页面。
5. 分别完成下面的测试矩阵。第一次只验证进入收银台，不点击最终付款；第二次再在明确确认后完成实际支付。

支付链接只在 EasyInput 进程和临时本机页面的内存中存在。页面 15 分钟后停止服务，不写入应用配置或普通日志。

## 测试矩阵

| 编号 | 入口 | 扫码/打开环境 | 预期结果 | 记录内容 |
|---|---|---|---|---|
| A1 | 二维码 | 微信扫一扫 | 进入本次订单支付页 | 最终域名、是否要求登录、金额是否一致 |
| A2 | 二维码 | 系统相机或浏览器扫码 | 能打开，或明确提示必须在指定 App 中打开 | 错误提示和跳转链 |
| A3 | 页面按钮 | Mac 默认浏览器 | 能进入支付页，或给出可理解的环境限制 | 浏览器类型、最终域名 |
| A4 | 二维码 | 不同网络的手机 | 不依赖电脑本机地址，仍能打开官方 H5 | Wi-Fi/蜂窝网络差异 |
| B1 | 微信扫码 | 完成一次低金额支付 | 页面显示成功 | 成功时间、回跳地址 |
| B2 | MCP | 支付后调用 `query-order` | 状态变为已支付 | 从付款到状态更新的延迟 |
| C1 | 过期链接 | 任意环境 | 明确提示订单或链接已过期 | 是否会错误进入旧订单 |

## 通过标准

- 二维码内容是原始 HTTPS `payH5Url`，不是 `localhost` 地址；
- 至少一种主流扫码入口能够进入正确订单的官方支付页；
- 页面金额和订单号与 `create-order` 结果一致；
- 支付过程不要求复制 Token、手机号或地址；
- 支付完成后，`query-order` 能在可接受时间内返回已支付；
- 过期链接不会复用旧价格或错误创建新订单。

如果 A1、B1、B2 全部通过，就可以把该二维码页接入语音 Function Calling 的 `mcd_submit_order` 结果处理。若 A1 失败但 A3 成功，正式方案应改成“直接打开支付 H5”，不再把二维码作为主入口。

## 安全边界

- 验证页面不嵌入远端 iframe，避免 CSP、第三方 Cookie 和点击劫持问题；
- 只接受 HTTPS URL，拒绝带 URL 用户名或密码的链接；
- 本机服务只监听 `127.0.0.1`，使用随机端口和随机路径；
- 响应设置 `no-store`、`no-referrer`、CSP 和禁止被嵌入的安全头；
- MVP 只对 `mcd.cn` 域名给出提示，不强制拦截其他域名，因为真实支付可能跳转到麦当劳的支付合作方；正式上线前必须根据真实样本建立域名白名单。
