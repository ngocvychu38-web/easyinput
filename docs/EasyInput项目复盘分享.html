04 / THE PIVOT
04 / 12

实时语音的第一版思路，
为什么放弃

链路越长，延迟和插话状态越难控制。

V1 / CLASSIC PIPELINE

每一步都要等上一步

语音→ASR→LLM→TTS
  • 延迟不断叠加
  • 用户插话时，要协调识别、模型、播放三层
  • 能做出来，却不像自然通话
→切换思路
V2 / REAL-TIME MODEL

端到端实时语音

连续声音→实时会话→流式声音
  • 文字理解、对话、语音输出在同一会话里完成
  • 支持取消当前回答
  • 更适合“通话”，而不是语音按钮
05 / LIVE LOOP
05 / 12

一次实时通话，如何跑起来

边收、边处理、边播放，声音不再排队等候。

用户说话按下实时通话键
键盘上行持续上传麦克风
豆包返回识别文字 + 回复声音
键盘下行流式送入扬声器
中途插话客户端取消旧回答
20 ms一小段声音

音频规格

小片段流式传输，让体验更像真实通话。

上行声音16 kHz
下行声音24 kHz
播放策略边生成边播
打断策略取消 + 清队列

07 / FUNCTION CALLING
07 / 12

Function Calling 的
正确顺序

不要被“输入 / 输出”标签带偏，先记住业务顺序。

01

客户端告诉豆包：我有哪些工具

把已启用的动作注册进会话

02

用户说：打开微信

实时语音会话持续进行

03

豆包下发 function_call

请求调用“打开微信”

04

客户端执行并回传结果

成功或失败都作为 tool 消息返回

05

豆包继续用语音回答

模型知道动作已经完成

DEBUG NOTE / VOLCENGINE

服务端先发要求，
客户端执行后回传。

如果方向理解反了，客户端和模型会互相等待：没有打开应用，也没有回答。

server → function_call_arguments.done
client → conversation.item.create / role=tool
08 / WHEN IT BREAKS
08 / 12

“刚才还可以”，
为什么聊一会儿就失灵

不是一个 Bug，是多层链路同时出问题。

模型说“没有可用工具”
“剪映”“Codex”识别不准
听懂了，却只给文字回答
扬声器声音被麦克风收回去
重复工具消息导致动作重复

把玄学变成可定位的链路

在每一个关键节点记录证据。

SESSIONtools_loaded = 3
ASRtext = “打开微信”
MODELfunction_call = open_app
CLIENTmatched = WeChat.app
AUDIOecho_detected = true
RESULTtool_result = success
LOG FIRST · GUESS LAST
09 / MAKE IT RELIABLE
09 / 12

不是所有事情，
都要交给大模型

确定的事情走确定路线，复杂的事情才交给模型。

DIRECT ROUTE

明确、无参数命令

客户端识别后直接执行，快、稳、可预期。

  • 打开微信
  • 打开剪映
  • 打开 Codex
  • 严格匹配完整命令
MODEL ROUTE

需要理解上下文的命令

继续交给 Function Calling，模型负责选择工具和生成参数。

  • 把选中的文字改得更正式
  • 翻译成英文
  • 快捷键 / 复制粘贴
  • 复杂内容编辑
配套增强：应用名热词 · 受限模糊匹配 · 回声剥离 · 调用去重 · 本地执行后取消普通回答
10 / CLEAR BOUNDARIES
10 / 12

客户端、固件、云端，
分别负责什么

边界越清楚，系统越容易扩展，也越安全。

ROLE 01

固件

负责
通话触发、采集麦克风、播放扬声器、保持音频连接
不负责
不认识微信，不执行 Function Calling
ROLE 02

Mac 客户端

负责
保存映射、连接云端、执行本机动作、记录日志
不负责
不代替模型理解复杂语言
ROLE 03

豆包实时语音

负责
识别、对话、生成语音、复杂工具选择
不负责
不直接控制用户电脑
下一步： AEC 回声消除 + 稳定的全双工音频。文字过滤只是补救，理想解法仍在音频前端。
